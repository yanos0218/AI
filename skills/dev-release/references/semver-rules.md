# SemVer 세부 판단 기준

SKILL.md §1의 보충. 저장소에 `docs/versioning.md`나 README 버전 정책이 있으면 그쪽이 우선한다.

## 1. 커밋 타입 → 등급 매핑

| 커밋 | 최소 등급 |
| --- | --- |
| `feat!:`, 본문 `BREAKING CHANGE:` | MAJOR |
| `feat:` | MINOR |
| `fix:`, `perf:`, `refactor:`, `style:` | PATCH |
| `docs:`, `test:`, `chore:`, `ci:` 만 있음 | 버전 변경 없음(사용자가 원하면 PATCH) |

커밋 메시지가 규칙을 안 따르면 `git diff <tag>..HEAD --stat`와 실제 변경을 보고 직접 분류하고, 분류 근거를 보여준 뒤 확인받는다. **등급을 낮추려고 breaking change를 빠뜨리지 않는다** — 사용자가 못 보고 넘어가면 실제 장애로 이어진다.

## 2. 저장소 유형별로 "무엇이 breaking인가"가 다르다

| 유형 | MAJOR로 보는 것 | 버전이 보통 박히는 곳 |
| --- | --- | --- |
| 웹앱 / PWA | 데이터 스키마·데이터 소스 전환, UI 전면 개편 | git 태그, README 배지. 캐시 무효화용 값(서비스워커 캐시명 등)은 SemVer가 아니므로 혼동 금지 |
| 운영 스크립트 / CLI | 사용 절차·입출력 계약·상태 파일·복구 방식이 달라짐 | 스크립트 안 버전 상수, checksum, 폴더 README의 현재 버전·Version History 표 — 전부 같은 커밋에서 |
| 단일 파일 도구(HTML 등) | 결과 수치·화면 구조가 "다시 배워야 할 만큼" 달라짐 | 파일 안 버전 표기 + README 히스토리 표. 두 자리(`X.Y`)를 쓰는 저장소도 있으니 §0 확인 |
| 문서 / 자동화 시스템 | 작업 흐름 전면 개편, 구조 재설계 | README 헤더 버전, CHANGELOG |
| 태그를 쓰지 않는 저장소 | — | 날짜순 CHANGELOG만. 스코프·이력은 짝 저장소 문서가 담당하는 경우가 있음 |

각 저장소의 실제 기준은 그 저장소 README/docs에 있다. 이 표는 "어디를 봐야 하는지"를 알려주는 용도다.

## 3. 0.y.z (정식 출시 전)

- 저장소 문서에 Phase 로드맵이 있으면 그걸 따른다.
- 없으면 기본: breaking → MINOR(y), 기능·수정 → PATCH(z). `1.0.0`은 "외부 사용자에게 URL/파일을 공유해 실제로 쓸 수 있는 시점"에 사용자가 결정한다.

## 4. 판단이 갈릴 때 자주 나오는 경우

- **기능 추가 + 버그 수정 혼재** → MINOR. 릴리즈 노트 `## 메모`에 "신규 기능 포함이라 MINOR" 한 줄을 남기면 나중에 이유를 다시 찾지 않아도 된다.
- **감사(audit) 결과 일괄 적용** — 수정만 있으면 PATCH. 사용자 눈에 띄는 동작 변화(상한 추가, 필드 제거 등)가 섞이면 MINOR로 올리고 노트에 명시.
- **문서만 대량 재구성** — 버전 변경 없음. 노트를 쓰고 있다면 `## 메모`에만.
- **의존성 업데이트** — 동작 변화 없으면 PATCH, 사용자에게 보이는 변화가 있으면 그 변화의 등급.
- **두 자리 체계(`X.Y`)인 저장소** — `Y`는 9를 넘어도 계속 올린다(`2.9` → `2.10`). `X`는 "다시 배워야 할 때"만.
