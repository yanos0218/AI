# dev-workflow

어떤 저장소든 "파일이 어디에 있고, 무엇을 돌리면 됐다고 말할 수 있는지"를 정해 두고 그 기준으로 일한다.

용어는 사용자 정의를 따른다.

- **파일** = 실제 데이터가 든 개별 자료. **폴더** = 파일·하위 폴더를 담는 공간.
- **산출물** = 과정 중에 생기는 것(테스트 문서, 구조표, 테스트 파일, CI 잡). **결과물** = 최종적으로 전달되는 성과(검증된 기능·문서).
- 산출물은 저장소에 남기고, 결과물은 **증거(실행한 명령과 출력)** 와 함께 보고한다.

## 0. 시작 전 확인 (필수)

| 확인 | 있으면 |
| --- | --- |
| `docs/testing.md`, `tests/README*` | 테스트 방법은 그 문서가 정답. 새로 만들지 않고 빠진 절만 제안 |
| `CONTRIBUTING.md`, 저장소 `CLAUDE.md` | 구조·이름 규칙·PR 체크리스트 우선 |
| `.github/workflows/*.yml` | CI가 돌리는 명령 = 공식 테스트 명령. 로컬 명령은 이것과 같아야 함 |
| `package.json` scripts, `build.gradle`, `pyproject.toml`, `Makefile` | 테스트 명령의 원천 |

발견한 것을 사용자에게 한 줄로 알린 뒤 진행한다.

## 1. 요청 종류별 절차

**A. 테스트 방법 정의** — "테스트 어떻게 해 / 방법 정리해줘 / 규칙 만들어줘"

```text
테스트 방법 정의
- [ ] 1. §0 확인 결과 한 줄
- [ ] 2. 스택 판별 → references/testing-guide.md 표에서 명령 선택 → 직접 한 번 실행해 되는지 확인
- [ ] 3. docs/testing.md 초안 (틀: references/testing-guide.md §2). 없는 테스트는 만들지 않고 "아직 없는 것"에 적는다
- [ ] 4. CI 명령과 로컬 명령이 같은지 대조
- [ ] 5. ★ 사용자 확인 ★ 후 커밋. 저장소 CLAUDE.md·PR 템플릿에서 testing.md를 가리키게
```

**B. 파일·폴더 정리** — "파일 정리해줘 / 폴더 구조 잡아줘 / 어디에 둬야 해"

1. `git ls-files`로 현재 구조를 표로 만든다. 스택 표준은 `references/file-layout.md`.
2. 옮길 것·지울 것·그대로 둘 것을 **제안표**로 보이고 사용자 확인을 받는다.
3. 이동은 `git mv`, 삭제는 항목마다 확인. 옮긴 뒤 그 경로를 `**/*.md`·스크립트에서 grep해 참조를 같은 커밋에서 고친다.

**C. 결과물 보고** — "테스트 돌리고 결과 보여줘", 또는 기능 작업을 끝냈을 때

§0에서 찾은 명령을 실행하고 **실행한 명령 + 출력 요약**을 보고한다. 실행하지 못했으면 "미검증"이라고 쓴다. 문법 검사만 통과한 것을 "테스트 통과"라고 쓰지 않는다.

## 2. 참고 자료

- `references/testing-guide.md`
  - 스택별 테스트 명령 표와 `docs/testing.md` 틀. A일 때 읽는다.
- `references/file-layout.md`
  - 표준 폴더 구조, 이름 규칙, 정리 절차. B일 때 읽는다.

## 하지 않는 것

- 파일 삭제·대량 이동을 사용자 확인 없이 하지 않는다
  - 되돌리기 어렵다.
- 다른 저장소의 `testing.md`를 복사해 오지 않는다
  - 형식만 따르고 내용은 이 저장소 것이어야 한다.
- 테스트가 없는 저장소에 테스트 프레임워크를 임의로 도입하지 않는다
  - 최소 검사(문법·린트)를 제안하고 사용자가 고른다.
- 릴리즈·배포는 하지 않는다.
