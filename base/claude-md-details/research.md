# 조사·저장소 상태 수정 세부 규칙

전역 `CLAUDE.md` §5에서 옮겨 온 규칙. 조사를 하거나 저장소 상태(Release·배포 설정)를 고치기 전에 읽는다.

- 조사는 공식 문서 먼저, 커뮤니티 글은 날짜를 보고 1년 넘으면 "확인 필요"를 붙인다. 명령·옵션·설정 키는 직접 실행해 확인하고, 못 했으면 "미검증". 답변 끝에 출처를 남긴다. 사용자가 요청한 조사와 결정에 쓴 조사는 결정에 안 쓰였더라도 GitHub Issue에 `research` 라벨로 기록한다(이슈를 쓰는 저장소면).
  - 도구·사례 조사는 표본을 정량으로 뽑는다(검색 API를 여러 검색어·스타 순으로, awesome 목록 교차). 도구마다 스타·최근 활동을 직접 확인하고, 스타 100 미만은 "소규모"로 표시한다.
  - "없다"고 쓰지 않고 찾아본 범위(검색어·채널·건수)를 적는다. 주장마다 확인·부분 확인·미확인을 붙인다.
  - 서브에이전트 조사 결과는 보고 전에 핵심 사실(존재·수치·날짜)을 직접 재검증한다. (2026-09-27, 검증 없이 옮긴 비교 조사가 스타 13개·0개 저장소를 주 근거로 쓴 사례)
- `--limit`/페이지네이션 기본값이 있는 조회(예: `gh release list`)를 "전체 목록"으로 오인하지 않는다. 전체가 필요하면 총 개수부터 확인한다. (2026-09-17, kolo_pwa에서 `gh release list` 기본 `--limit 10`을 전체로 착각해 31개 중 21개 릴리즈를 누락한 사례)
- 저장소 상태(GitHub Release, 배포 설정 등)를 직접 고치기 전에 그 영역을 위한 절차·자동화가 이미 문서화돼 있는지 먼저 확인하고, 있으면 그 절차를 따른다. 부득이 파생 산출물을 먼저 고쳤다면 원본 소스 파일도 같은 자리에서 동기화한다. (2026-09-17, kolo_pwa `.github/release-notes/` + `release.yml`이 이미 있는데 `gh release edit`으로 직접 우회해 원본과 실제 Release가 어긋난 사례)
