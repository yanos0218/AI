# 공통 지침

모든 저장소에 적용되는 규칙만 둔다. 저장소별 규칙(배포, 테스트, 확정된 사실)은 각 저장소의 `CLAUDE.md`/`docs/`가 담당하고, 충돌하면 저장소 쪽을 따른다. 여기에 줄을 추가할 때는 "이 줄이 없으면 Claude가 실제로 실수하는가?"가 예일 때만.

## 1. 언어

- 직접 쓰는 문장은 전부 한국어 — 채팅 답변, 도구 호출의 `description`/`prompt`/`args`, 커밋 메시지 제목까지. 코드·식별자·명령어·파일명·고유명사는 원문 그대로.
- 짧은 필드라고 예외로 두지 않는다. 애매하면 한국어.

## 2. 답변

- 첫 문장은 결론 또는 결과. 배경·과정 설명은 사용자가 물을 때만.
- 채우기말("좋은 질문입니다"), 앞서 한 말의 반복, 택하지 않을 선택지 나열은 쓰지 않는다.
- 선택지를 줄 땐 추천 하나를 먼저, 이유는 한 줄. 사용자는 개발자가 아니므로 용어는 괄호로 짧게 푼다.
- 동의하지 않으면 그렇게 말한다.
- 정의된 규칙(이 파일, 저장소 `CLAUDE.md`, `docs/`)에서 스스로 벗어나지 않는다. 벗어나야 할 이유가 생기면 멈추고 근거를 찾아 제안하고, 승인되면 규칙 문서를 먼저 고친 뒤 진행한다.

## 3. 확인 기준

**묻지 않고 진행**: 읽기·검색, 로컬 편집, 테스트·빌드·린트 실행, 브랜치 생성, 스크래치패드 작업, 명백한 기본값이 있는 선택(고른 뒤 한 줄로 알림), **작업 단위가 끝났을 때의 로컬 커밋**(되돌리기 쉬움 — 메시지에 무엇을 했는지만 정확히).

**확인 후 진행**: `git push`(태그 포함), 릴리즈·배포·publish, 원격 브랜치/태그 삭제, 파일 삭제, 내가 만들지 않은 파일 덮어쓰기, 외부 서비스 쓰기(메일·게시·API·저장소 설정), 유료·한도 리소스 사용.

확인 후 진행 항목 중 방법이 하나가 아니라 여러 개 있는 경우(예: 릴리즈 등급 선택, 배포 순서 조정, 삭제 대상 선택)는 훅이 실행 직전에 뜨는 순간이 아니라 계획을 세우는 단계에서 AskUserQuestion으로 방법부터 확정한다. 방법이 하나뿐이면 이 단계 없이 바로 실행하고 훅의 확인만 받는다.

**배치 = 사용자 메시지 하나가 요청한 작업 전체.** "진행해줘", "배포까지"처럼 끝을 지정하면 그 끝까지의 확인 항목은 한 번에 승인된 것으로 보고 중간에 다시 묻지 않는다. 승인은 그 배치에만 유효하고, 다음 메시지는 다시 확인한다. 배치 안에서 계획에 없던 확인 항목이 새로 생기면 그때만 묻는다. 이 목록은 `~/.claude/hooks/git-guardrails.sh`(PreToolUse 훅)가 강제하므로, 훅이 확인을 요구하면 우회하지 않는다.

## 4. 검증

- 코드를 바꿨으면 그 저장소의 테스트/체크를 실제로 실행하고 **실행한 명령과 결과**를 함께 보고한다.
- 문법 검사만 통과한 것을 "테스트 통과"라고 쓰지 않는다. 실행 못 했으면 "미검증"이라고 쓴다.
- UI·라이브 서비스는 직접 띄우거나 응답을 받기 전엔 "동작 확인"이라 쓰지 않는다.
- 실패하면 출력을 그대로 보여준다. 원인 파악 없이 같은 시도를 반복하지 않는다.

## 5. 컨텍스트

- 세션 시작 시 저장소 `CLAUDE.md` → `README.md` → 문서 인덱스(`docs/` 등) 순으로 읽는다. "확정된 사실"로 표시된 항목은 다시 검증하지 않는다.
- 같은 지적을 두 번 받거나 실수가 실제 문제로 이어졌으면, 그 저장소 `CLAUDE.md`에 "날짜 + 무슨 일 + 앞으로의 규칙" 형식으로 기록을 제안한다. 저장소를 가리지 않는 규칙이면 이 파일.
- 저장소 `CLAUDE.md`에 정기 점검 항목이 있으면 세션 시작 시 날짜를 확인해 제안만 한다. 자동 실행하지 않는다.
- GitHub 저장소를 열었는데 저장소 표준(CI에서 markdownlint·테스트, `CHANGELOG.md`, 저장소 `CLAUDE.md`, 발견한 문제는 Issue — 원본은 claude-config `docs/repo-standard.md`)에 빠진 게 있으면 **세션당 한 번만** 제안한다. 만들지는 않는다. 거절하면 그 저장소에 `.claude/.no-repo-setup-suggest`(빈 파일)를 만들어 다음부턴 묻지 않는다.
- 컴팩션(대화 요약) 때는 수정한 파일 목록, 실행한 테스트 명령과 결과, 아직 안 끝난 체크리스트 항목을 반드시 보존한다.
- 파일을 많이 읽어야 하는 조사·감사·로그 분석은 서브에이전트에 맡기고 요약만 받는다. 본 대화에 원문을 쌓지 않는다. 서브에이전트와 시험 세션은 Sonnet으로.
- 정지(TaskStop)시킨 서브에이전트가 뒤늦게 결과를 보내면, 검증 없이 반영하지 않는다 — 직접 재확인한다(2026-09-13, 이미 죽었다고 본 서브에이전트가 16분 뒤 보낸 보고에 승인 우회 시도가 섞여 있었던 사고).
- 여러 서브에이전트에 병렬로 위임할 때는 서로 겹치지 않는 파일 집합을 배정한다 — 겹치면 나중에 끝나는 쪽이 먼저 것을 조용히 덮어쓴다.
- 조사는 공식 문서 먼저, 커뮤니티 글은 날짜를 보고 1년 넘으면 "확인 필요"를 붙인다. 명령·옵션·설정 키는 직접 실행해 확인하고, 못 했으면 "미검증". 답변 끝에 출처를 남긴다. 결정에 쓴 조사는 GitHub Issue에 `research` 라벨로 기록한다(이슈를 쓰는 저장소면).

## 6. 문서 동기화

- 코드를 바꾸면 그것을 설명하는 문서(README, `CHANGELOG.md`의 `[Unreleased]`, 진행 보드 등 저장소에 있는 것)를 **같은 커밋**에서 갱신한다. 몰아서 하지 않는다.
- 파일·함수·설정을 삭제하거나 대체하면 그 이름을 `**/*.md`에서 grep해 참조하던 문서도 같은 커밋에서 고친다.

## 7. Git

- 커밋은 작업 단위(요청 하나가 끝나는 지점)마다 한다. 형식은 Conventional Commits `type(scope): 한국어 제목`. breaking change는 `feat!:` 또는 본문 `BREAKING CHANGE:`.
- `git reset --hard`, `git clean`, `checkout --` 전에 `git status`. 훅은 `--no-verify`로 건너뛰지 않는다.
- `.env`, 토큰, 비밀번호는 커밋·문서·대화에 남기지 않는다. 노출됐으면 재발급.
- 토큰이 필요하면(릴리즈·API 호출 등) 먼저 `gh auth status` 같은 명령으로 있는지 확인하고, 없으면 멈추고 사용자가 `gh auth login`이나 환경변수로 직접 넣게 안내한다. 채팅에 붙여넣으라고 하지 않는다.
- 복합 명령에서 `cd <경로> && <명령>`을 쓰지 않는다. `cd` 뒤 상대 경로 읽기는 `Read` deny 규칙과 겹쳐 정적 분석이 안 돼 승인 프롬프트가 뜬다. `git -C <경로> ...`나 절대 경로를 쓴다.

## 8. 코드

- 요청 범위만 바꾼다. 요청하지 않은 파일은 수정하지 않고 "이것도 고칠 필요가 있어 보인다"고 말만 한다.
- 있지도 않은 상황에 대한 방어 코드·추상화·설정 옵션을 미리 넣지 않는다.
