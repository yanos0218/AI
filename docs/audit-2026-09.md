# 저장소 검토 2026-09-09 — 문제 · 제안 · 아이디어

이틀간 만든 것을 한 발 떨어져 보고, 커뮤니티의 개인 Claude 설정 저장소(플러그인 마켓플레이스형, dotfiles형)와 대조한 결과. 상태: **문제** = 지금 고쳐야 함, **제안** = 보드에 올림, **아이디어** = 조건이 되면, **보류** = 이유가 있어 안 함.

| 항목 | 값 |
| --- | --- |
| 파일 42개, 문서 1,166줄, 릴리즈 4회(v0.1.0~v0.4.0, 이틀) | 문서 비중이 큼 — 설정 저장소로는 정상 |
| 기본 영역 | 지침 1, 스킬 1(+초안 1), 훅 3, 설정 예시 1, VS Code 1 |

| 배포 | Windows만. Mac·Linux·웹 0 |
| 보드 | 열림 21, 진행 2, 완료 19 |

## 2. 문제 (고쳐야 함)

| # | 문제 | 왜 문제인가 | 조치 |
| --- | --- | --- | --- |
| P1 | **설치가 손으로 치는 `cp` 명령 4줄** | 기기 3대에 반복. settings.json 합치기는 손으로 하면 틀림. 커뮤니티는 예외 없이 스크립트(stow·chezmoi·setup.sh) | [C-44](PROGRESS.md#c-44) `tools/install.sh` — 멱등, settings 키 병합, 끝에 `check-install.sh` 실행 |
| P2 | 승격마다 릴리즈 컷 | 번호만 앞서감 | 완료 — versioning.md 컷 시점 3가지 |
| P3 | **정의한 규칙을 Claude가 스스로 어김** (P2가 그 예) | 규칙을 만드는 저장소에서 규칙을 어기면 다른 저장소에서도 어긴다 | 저장소 CLAUDE.md에 "규칙 이탈은 먼저 제안" 추가, 전역 지침 수정안 `drafts/claude-md/`([C-47](PROGRESS.md#c-47)) |
| P4 | HANDOFF "현재 상태"와 PROGRESS §0 표가 같은 정보를 두 번 | 한쪽만 갱신되면 어긋남(오늘 실제로 HANDOFF가 낡았음) | HANDOFF 현재 상태는 **4줄 이하 + 링크**로 제한(CLAUDE.md 문서 규칙) |
| P5 | auto memory가 기기 로컬 | Mac에서 쌓인 교정을 Windows가 모름 | [Issue #9](https://github.com/yanos0218/AI/issues/9)에 포함: 월 점검 때 `memory/*.md`를 `drafts/observations/memory-<기기>/`로 복사 |
| P6 | 스킬 발동 테스트가 손 절차 | 오늘 두 번 같은 코드를 다시 짬 | [C-46](PROGRESS.md#c-46) `tools/test-skill.sh <스킬> <시나리오 폴더>` |
| P7 | 관찰 파일 하나에 두 날짜 내용 | 날짜 파일 규칙 위반 | 규칙: 하루 하나. 다음부터 적용 |

## 3. 제안 (커뮤니티 대조에서 나온 것)

| # | 제안 | 커뮤니티 근거 | 판단 |
| --- | --- | --- | --- |
| S1 | **플러그인화** — `base/skills` + `base/hooks`를 `.claude-plugin/plugin.json` + `hooks/hooks.json`으로 묶고 이 저장소를 개인 마켓플레이스로. 기기마다 `claude plugin install`, 갱신은 `claude plugin update` | 2026 개인 설정 저장소의 주류(markky21/claude-skills 등). 버전은 `plugin.json`이 관리 | **검토** [C-45](PROGRESS.md#c-45). 단 CLAUDE.md·permissions·statusLine은 플러그인에 못 실으므로 `install.sh`는 여전히 필요. 둘 다 유지하는 비용 대비 이득을 Mac 설치 때 판단 |
| S2 | Stop 훅으로 "PROGRESS·HANDOFF 갱신했나" 확인 | docs drift 방지 훅이 흔함 | **검토** [C-48](PROGRESS.md#c-48) — 이 저장소 `.claude/settings.json`에만. 세션 끝마다 뜨는 소음이 되면 끔 |
| S3 | `~/.claude/rules/` 모듈 | 공식 기능, 기본 CLAUDE.md 비대화 방지 | 이미 [C-42](PROGRESS.md#c-42) |
| S4 | 서브에이전트 정의(`agents/`) — 월 점검용 "audit" 에이전트 | 개인 저장소들이 리뷰·감사 에이전트를 둠 | **아이디어** — 월 점검 항목이 확정된 뒤 |
| S5 | `/insights` 월 1회 | 공식 | 이미 [C-25](PROGRESS.md#c-25) |
| S6 | MCP 서버 | 커뮤니티 설정의 단골 | **보류** — 필요한 외부 데이터가 없음. `gh` CLI로 충분 |
| S7 | 스킬에 `allowed-tools` 프런트매터로 사전 승인 | 공식 기능. 스킬 실행 중 승인 프롬프트 감소 | **제안** — dev-release에 `Bash(git tag *)`, `Bash(gh release view *)` 등. [C-11](PROGRESS.md#c-11)과 함께 |

## 4. 잘 되고 있는 것 (유지)

- 기본/초안 분리 + 훅 강제 — 커뮤니티 저장소 대부분은 이 구분이 없어 "무엇이 검증됐는지" 모름.
- 문서 상한 + CI 검사 — CLAUDE.md 200줄 규칙을 CI로 지키는 저장소는 드묾.
- 발동 테스트를 새 세션(`claude -p`)으로 — 대부분은 같은 세션에서 `/skill`을 쳐 보고 끝냄.
- 관찰 기록 → 월 점검 → 후보 → 승격의 흐름.
