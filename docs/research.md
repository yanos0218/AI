# 조사 규칙 — 최신·검증·기록

질문: 정보를 찾을 때 최신 위주로 찾고 검증까지 하도록 돼 있나? 찾은 내용은 다시 쓸 수 있게 기록해 두나?
답(2026-09-09): **둘 다 규칙으로는 없었다.** 지금까지는 검색어에 연도를 넣고 공식 문서를 먼저 읽는 습관으로 때웠고, 조사 결과는 각 문서의 "참고" 절에 흩어져 있다. 아래가 그 빈자리를 채우는 규칙이다. 전역 지침 반영은 [Issue #40](https://github.com/yanos0218/AI/issues/40).

## 1. 왜 조심해야 하나

- Claude의 지식은 특정 시점에서 멈춰 있고(모델 공개 시점 기준 수개월 전), 오늘 날짜와의 간격만큼 틀린 정보가 섞인다. Claude Code는 몇 주 단위로 기능이 바뀌므로 특히 그렇다.
- 웹 검색 결과에는 오래된 글, 다른 도구 이야기를 섞어 쓴 글, AI가 쓴 요약 글이 많다. 커뮤니티 글 하나를 근거로 설정을 바꾸면 없어진 기능이나 바뀐 문법을 따를 수 있다.
- WebFetch는 같은 URL을 15분 캐시하고, 검색 요약은 원문이 아니다.

## 2. 조사 규칙

| 순서 | 규칙 | 방법 |
| --- | --- | --- |
| 1 | **공식 문서 먼저** | Claude Code는 `code.claude.com/docs/llms.txt` 인덱스에서 페이지를 찾아 원문을 읽는다. GitHub·VS Code 등도 각 공식 문서. 커뮤니티 글은 공식에 없는 "실제 써 본 경험"을 얻을 때만 |
| 2 | **날짜를 본다** | 검색어에 올해 연도. 글에 날짜가 없거나 1년 넘었으면 답변에 "(구 자료, 확인 필요)"를 붙인다. 없어진 기능·이름이 바뀐 명령이 흔함 |
| 3 | **사실은 실행으로 검증** | "명령이 있다/옵션이 있다"는 `--help`·`--version`·실제 실행으로 확인한다. 설정 키는 `$schema` 검증. 실행 못 하면 "미검증" |
| 4 | **교차 확인** | 결정에 영향을 주는 사실은 독립 출처 둘(공식 + 실행, 또는 공식 + 커뮤니티) 이상. 하나뿐이면 그렇게 말한다 |
| 5 | **출처와 조사일을 남긴다** | 답변 끝에 Sources, 문서에는 "참고" 절 + 조사일. 링크 없는 주장은 쓰지 않는다 |
| 6 | **모르면 모른다고** | 검색해도 확인이 안 되면 추측을 사실처럼 쓰지 않는다 |

## 3. 재사용 — 조사 기록

같은 것을 두 번 찾는 일이 실제로 있었다(플러그인·Actions 한도·메모리 기능). 결정에 쓰인 조사는 **GitHub Issue에 `research` 라벨을 붙여** 남긴다. 파일과 이슈에 이중으로 남기지 않는다.

이슈 본문 형식과 재사용 절차는 [docs/issue-format.md](issue-format.md) "조사" 절 — 형식은 거기 하나로 관리한다.

- 이미 문서 본문에 녹아 있는 조사(GitHub 활용, 설정 층 구조, 저장소 검토)는 그 문서가 기록이다.
- Claude의 auto memory `reference` 타입은 "어디를 보면 되는지"만 담는 포인터로 쓰고, 조사 내용 자체는 이슈에 둔다.
- 2026-09-13 이전 조사는 `docs/research/`에 파일로 남아 있다(archive, 새로 안 만듦).
  - 색인은 [docs/research/README.md](research/README.md).

## 4. 도구·사례 조사 보강 (2026-09-27)

같은 날 같은 주제(사용량 대시보드 비교)로 두 번 조사했는데 비교 대상이 서로 달랐고, 두 번째 조사는 스타 13개·0개짜리 저장소를 주 비교 대상으로 썼다. 메인이 직접 GitHub 검색을 돌려 보니 관련 저장소가 937개였고 스타 1천~2천대 도구 여러 개가 두 조사 모두에서 빠져 있었다. 서브에이전트 결과를 검증 없이 옮긴 것이 원인이다([Issue #136](https://github.com/yanos0218/AI/issues/136)).

| 규칙 | 방법 |
| --- | --- |
| 표본은 정량으로 뽑는다 | `gh api -X GET search/repositories -f q='<검색어>' -f sort=stars`를 검색어 여러 개로 돌리고, 인기 awesome 목록도 확인<br>검색어별 총 결과 수와 선정 기준(스타·최근 활동)을 기록 |
| 비중을 같이 적는다 | 도구마다 스타 수·최근 push 날짜를 `gh api`로 직접 확인해 적는다(검색 요약의 숫자를 옮기지 않음)<br>스타 100 미만은 "소규모"로 표시하고 결론의 단독 근거로 쓰지 않는다 |
| "없다"고 쓰지 않는다 | "검색어 ○개·채널 ○곳·○건 확인 범위에서 못 찾음"처럼 범위를 함께 쓴다 |
| 서브에이전트 결과는 메인이 재검증한다 | 보고 전에 인용된 저장소의 존재·스타·날짜와 핵심 수치를 메인이 직접 확인(`gh api`, 원문)<br>틀린 것은 고치고, 확인 못 한 것은 "미확인"으로 바꿔 전달 |
| 이전 조사와 대조한다 | 같은 주제의 조사 이슈 본문과 결론이 달라지면 무엇이 왜 달라졌는지 적는다 |
| 확인 수준을 표시한다 | 주장마다 확인(원문 직접)·부분 확인·미확인 |
