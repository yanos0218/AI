# 공통 지침

## 소통

- 사용자와의 대화는 한국어로 한다.
- 코드/커밋 메시지/변수명 등은 관례를 따르되(주로 영어), 설명과 요약은 한국어로 한다.
- 답변은 간결하게. 불필요한 서론이나 요약 반복은 하지 않는다.

## 커밋 메시지

- [Conventional Commits](https://www.conventionalcommits.org/) 형식을 따른다: `type(scope): subject`
- 주로 쓰는 type: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`
- breaking change는 `!`(예: `feat!:`) 또는 본문에 `BREAKING CHANGE:`로 명시한다.
- 커밋은 사용자가 명시적으로 요청했을 때만 만든다.

## 작업 후 확인

- 코드를 변경했으면 관련 테스트를 실행하고 결과를 보고한다. 테스트가 없거나 실행할 수 없으면 그 사실을 명확히 말한다.
- 실제로 검증하지 않은 것을 검증했다고 말하지 않는다 (예: UI는 직접 켜서 확인하기 전엔 "동작 확인"이라고 하지 않는다).

## 되돌리기 어려운 작업

- push, force-push, 원격 브랜치/태그 삭제, 배포(publish/release) 등은 사용자 확인 없이 실행하지 않는다.
- `git reset --hard`, `git clean`처럼 로컬 변경을 날릴 수 있는 명령 전에는 `git status`로 먼저 확인한다.

## 코드 스타일

- 요청받은 범위 이상으로 리팩터링하지 않는다. 버그 수정은 버그 수정만 한다.
- 필요 없는 주석은 달지 않는다. 코드만 봐서 알 수 없는 이유(왜 이렇게 했는지)가 있을 때만 짧게 남긴다.
- 존재하지 않을 상황에 대한 방어 코드/에러 처리를 미리 추가하지 않는다.
